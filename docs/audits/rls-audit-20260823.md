# ConsultX — Production RLS Audit

**Project:** `hrnltxmwoaphgejckutk`
**Date:** 2026-08-23
**Method:** Direct read-only inspection of the production database over the
transaction pooler (port 6543), plus role-impersonation probes inside
transactions that were rolled back. No production data was modified.
**Scope:** Every table in schema `public` (47 tables), every RLS policy.

This audit closes the `RLS — PARTIAL` line item from
`docs/audits/phase2-production-validation.md`.

## Legend

- **CONFIRMED** — observed directly in production, with the evidence shown.
- **LIKELY** — strong inference from code plus schema, not directly observed.
- **BY DESIGN** — open on purpose; recorded so it is a decision, not an accident.

---

## 1. Baseline — CONFIRMED

All 47 tables in `public` have RLS **enabled**. There is no table in the schema
that an authenticated user can read simply because RLS was forgotten.

Nine tables have RLS enabled with **zero policies**, which is deny-all for
`anon` and `authenticated`:

`corpus_coverage`, `document_tables`, `enterprise_case_counters`, `sbc_pages`,
`source_registry`, `source_versions`, `user_subscriptions`, `validation_runs`,
`webhook_dead_letters`

This is correct, not a gap: none of the nine is queried from `src/` (verified by
search for `.from("<table>")` across the client), and all server-side access
runs with the service-role key, which carries `BYPASSRLS`. Notably
`user_subscriptions` — the billing ledger — is unreachable from any browser
session.

## 2. CRITICAL — `mode_daily_usage` is readable and writable by anonymous callers

**Severity:** CRITICAL — entitlement bypass with direct cost impact.
**Status:** CONFIRMED. **Not yet fixed** — see Section 6.

### What is wrong

`public.mode_daily_usage` carries a policy whose name states the intent but
whose grant does not match it:

| policyname | cmd | roles | USING | WITH CHECK |
|---|---|---|---|---|
| `Service role full access to mode_daily_usage` | `ALL` | `{public}` | `true` | `true` |
| `Users can read own mode usage` | `SELECT` | `{public}` | `auth.uid() = user_id` | — |

The first policy was meant for `service_role`. It was created against the
PostgreSQL `PUBLIC` role instead, which includes `anon` and `authenticated`.
RLS policies are OR-ed, so this PERMISSIVE `ALL / true / true` policy overrides
the correctly scoped one beside it.

### Evidence

Run against production inside a transaction that was rolled back:

```sql
BEGIN;
SET LOCAL ROLE anon;
SELECT count(*) AS visible_rows, count(DISTINCT user_id) AS distinct_users
FROM public.mode_daily_usage;
ROLLBACK;
```

Result: **18 rows across 5 distinct users, with no JWT presented at all.**
The identical grant covers `INSERT`, `UPDATE` and `DELETE`.

The write path was deliberately **not** exercised against production. It does
not need to be: `pg_policies` reports `cmd = ALL` with `USING (true)` and
`WITH CHECK (true)`, which is conclusive.

### Why it matters

`mode_daily_usage` is the ledger behind the per-mode daily quotas
(`primary` / `standard` / `analysis`). Anyone holding the public anon key —
which ships in the frontend bundle by design — can set `count = 0` on any row,
or delete rows outright, and reset their own or any other user's daily limit at
will.

That defeats the server-authoritative entitlement enforcement the AI layer
depends on, and it carries a real bill: Advisory and Analytical both route to
`gemini-2.5-pro`. It also leaks per-user usage patterns to unauthenticated
callers.

### Why removing the policy is safe

Every read and write of this table goes through `SECURITY DEFINER` RPCs defined
in `supabase/migrations/20260404000001_restore_mode_rpcs.sql`:

`increment_mode_daily_count`, `decrement_mode_daily_count`,
`get_mode_daily_count`, `get_all_mode_daily_counts`

`SECURITY DEFINER` functions execute as the function owner and are unaffected
by RLS on the table. The edge functions additionally connect with the
service-role key (`BYPASSRLS`). Confirmed by search: **zero** direct
`.from("mode_daily_usage")` calls in `src/`, and **zero** in
`supabase/functions/`.

The correctly scoped `Users can read own mode usage` policy stays, so a
signed-in user can still read their own row.

## 3. HIGH — the entire SBC corpus is readable without logging in

**Severity:** HIGH — product IP exposure. **Status:** CONFIRMED.
**Recommendation:** tighten to `authenticated`. Requires owner sign-off because
it is a live frontend dependency.

| table | policy | roles | USING |
|---|---|---|---|
| `sbc_documents` (66 MB, 4,594 embeddings) | SELECT | `{public}` | `true` |

`public` includes `anon`, so the full retrieval corpus can be paged out by
anyone with the anon key, without an account.

This is **not** dead configuration — `src/components/ChatInterface.tsx:1907`
and `:1952` query `sbc_documents` directly from the browser to resolve citation
page ranges. Setting the table private would break the citation viewer, exactly
as it would for the `source-pdfs` bucket (see
`docs/audits/production-final-readiness.md`, Owner Action 2).

However, chat requires authentication, so narrowing the policy from `public` to
`authenticated` costs nothing functionally and removes anonymous scraping. That
is the recommended change; it is grouped with the `source-pdfs` decision because
both are the same question about the same content.

## 4. MEDIUM — knowledge graph and PII readable by any signed-in user

**Severity:** MEDIUM. **Status:** CONFIRMED.

| table | policy | roles | USING | note |
|---|---|---|---|---|
| `graph_nodes` (3.7 MB) | SELECT | `authenticated` | `true` | full KG dump |
| `graph_edges` (1.3 MB) | SELECT | `authenticated` | `true` | full KG dump |
| `community_summaries` | SELECT | `authenticated` | `true` | derived KG |
| `sbc_code_tables` | SELECT | `authenticated` | `true` | structured tables |
| `graph_indexing_status` | SELECT | `authenticated` | `true` | pipeline metadata |
| `user_public_profiles` | SELECT | `authenticated` | `true` | includes `phone` |

The five knowledge tables are consumed only by edge functions (service role);
no client code reads them. Their open `authenticated` grant therefore has no
functional purpose — any free-tier account can dump the whole knowledge graph.
Tightening these to zero policies would be behaviour-neutral.

`user_public_profiles` is different: it **is** read from the client
(`src/hooks/useOrganization.ts:441` and `:459`), and its open SELECT is
documented deliberately in the migration comment
(`20260426000007_enterprise_profiles_realtime_roles.sql`) so the workspace can
resolve names and avatars without joining `auth.users`. The concern is narrower:
the table also stores `phone`, so any authenticated user can enumerate every
user's phone number, not just their own organization's members. Scoping the
SELECT to co-members — or dropping `phone` from the client projection — would
close that without affecting the feature. Flagged as a product decision, not
changed.

## 6. Remediation — owner action required

The fix for Section 2 cannot be applied from this session for two independent
reasons: `.claude/hooks/guard-migrations.js` hard-blocks writes to
`supabase/migrations/`, and production writes are gated. The change itself is a
single reversible statement with no data mutation.

### Apply this in the Supabase SQL Editor

```sql
DROP POLICY IF EXISTS "Service role full access to mode_daily_usage"
  ON public.mode_daily_usage;

ALTER TABLE public.mode_daily_usage ENABLE ROW LEVEL SECURITY;
```

### Then verify — expect exactly one row

```sql
SELECT policyname, cmd, roles::text, qual, with_check
FROM pg_policies
WHERE schemaname = 'public' AND tablename = 'mode_daily_usage';
```

Expected: `Users can read own mode usage` / `SELECT` / `(auth.uid() = user_id)`.

### And confirm the hole is closed — expect 0

```sql
BEGIN;
SET LOCAL ROLE anon;
SELECT count(*) FROM public.mode_daily_usage;
ROLLBACK;
```

### Rollback if it ever breaks something

```sql
CREATE POLICY "Service role full access to mode_daily_usage"
  ON public.mode_daily_usage FOR ALL TO public
  USING (true) WITH CHECK (true);
```

Do not actually run the rollback — it re-opens the hole. If some future
component genuinely needs elevated access, scope it `TO service_role`, which
does not require a policy at all.

### After applying

Smoke-test the three chat modes and confirm the daily counters still increment
and still block at the limit. The RPCs are `SECURITY DEFINER` so nothing should
change, but the counters are the thing this policy touched.
